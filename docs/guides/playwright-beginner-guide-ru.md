## 1. Что вообще делает наш проект

У нас есть веб-приложение на `https://dev.slimkit.health/walking/survey/?stripeV64=true` — опросник для приложения по ходьбе. Опросник должен показываться на 10 языках: en, fr, it, es, ja, ru, de, pt, zh, ko.

**Какая логика выбора языка:** язык должен браться из браузера пользователя. Если у меня браузер на русском — приложение должно показать русский. Если на японском — японский. И т.д.

**Что мы автоматически проверяем:**

- Что на каждом из 10 языков показывается правильный перевод (не «сырой ключ» типа `intro_text_0`).
- Что вёрстка не ломается на длинных строках (например немецкий часто длиннее английского в 1.5 раза).
- Что финальный экран (paywall) показывает цену в правильном формате для каждой локали.
- Что всё это работает на 3 мобильных устройствах (iPhone 17, iPhone 16 Pro Max, Samsung S20e) и 2 движках браузера (Chromium = Chrome, WebKit = Safari).

Получается матрица `10 языков × 3 девайса × 2 движка = 60 комбинаций`. Каждая комбинация — это «project» в Playwright.

**Playwright** — это библиотека, которая умеет открывать браузер из кода и кликать там по элементам, как живой пользователь. У неё много встроенного: эмуляция мобильных устройств, разные локали, скриншоты, отчёты.

## 3. Первый запуск с нуля

Этот раздел про то, как взять чистый клонированный репо и довести его до «тесты бегут».

### 3.1 Перейти в папку проекта

```bash
cd "/Users/gigamike666/Web Projects/Manyas e2e"
```

### 3.2 Активировать нужную версию Node

В корне проекта есть файл `.nvmrc` со значением `20`. Команда `nvm use` сама подхватит правильную версию:

```bash
nvm use
```

Если выводит ошибку «Node not installed» — вернись к шагу 2.1.

### 3.3 Установить зависимости проекта

```bash
npm install
```

**Что это делает:** читает файл `package.json` и скачивает все библиотеки, от которых зависит проект (Playwright, TypeScript, xlsx-парсер и т.д.). Они складываются в папку `node_modules/` (она в `.gitignore`, не коммитим).

Может занять 1–3 минуты. В конце увидишь что-то вроде `added 250 packages in 47s`. Если ошибки — скриншот ошибку и спроси старшего разработчика.

### 3.4 Установить браузеры для Playwright

```bash
npm run install:browsers
```

**Что это делает:** Playwright не использует Chrome/Safari, которые установлены в системе. Он скачивает свои собственные версии Chromium и WebKit — гарантированно одинаковые на всех машинах. Это и есть «истинная кросс-браузерность».

Скачается ~500 МБ. Один раз и забыл.

### 3.5 Создать локальный файл `.env`

```bash
cp .env.example .env
```

Теперь открой `.env` любым редактором (например VS Code, или `nano .env`) и поставь реальные значения:

```
BASIC_AUTH_USER=dev
BASIC_AUTH_PASS=gPgFCeJ7
BASE_URL=https://dev.slimkit.health
SURVEY_PATH=/walking/survey/
FEATURE_FLAGS=stripeV64=true
```

**Зачем нужен `.env`:**

- В нём лежат секреты (логин/пароль). Файл в `.gitignore` — он НЕ попадёт в git.
- Программа читает оттуда переменные окружения, не нужно их прописывать руками каждый раз.
- Файл `.env.example` (в git, без секретов) показывает какие переменные надо заполнить.

**Никогда не коммить `.env`!** Если случайно сделал — крикни старшему, надо менять пароль.

### 3.6 Сгенерировать JSON-фикстуры переводов из xlsx

```bash
npm run i18n:import
```

**Что это делает:** в корне репо есть Excel-файл `WWLI Onboarding Localisation.xlsx` со всеми переводами (~1500 строк на каждый из 10 языков). Тесты не умеют читать Excel напрямую — наш скрипт разбирает его и складывает по файлу на каждый язык в `tests/fixtures/i18n/`:

- `en.json` — английский
- `ru.json` — русский
- ... и т.д.

Плюс создаётся `_meta.json` со статистикой импорта (сколько ключей, какие пропущены и почему).

**Зачем JSON а не Excel:**

- JSON в 1000 раз быстрее читается.
- JSON-ы можно сравнивать через `git diff` — видно что поменялось.
- JSON-ы можно коммитить и они нормально мержатся.

### 3.7 Первый прогон — smoke-тесты

Прежде чем гонять полную матрицу из 60 проектов (это ~45 минут), сначала прогони smoke — только английский язык на всех девайсах:

```bash
npm run test:smoke
```

Это 6 проектов × несколько тестов = быстрый прогон (~3–5 минут).

**Если всё зелёное** — проект настроен правильно, можно гонять полную матрицу или писать новые тесты.

**Если что-то красное** — см. раздел 7 «Что делать, если тест упал».

## 4. Как читать структуру проекта

```
Manyas e2e/
├── playwright.config.ts          ← Сердце Playwright. Описывает 60 projects.
├── package.json                  ← Зависимости + npm-скрипты.
├── tsconfig.json                 ← Настройки TypeScript-компилятора.
├── .env                          ← Твои локальные секреты. НЕ КОММИТИМ.
├── .env.example                  ← Шаблон для других разработчиков.
│
├── src/                          ← Наш «исходный код», классы и утилиты
│   ├── config/                   ← Конфиги: список языков, девайсов, projects
│   ├── fixtures/                 ← Playwright-fixture, который инжектит переводы в тесты
│   ├── pages/                    ← Page Object Model — классы для экранов
│   └── utils/                    ← Утилиты (импорт xlsx, проверки overflow, и т.п.)
│
├── tests/                        ← Тесты + ТЕСТОВЫЕ ДАННЫЕ
│   ├── fixtures/i18n/            ← JSON с переводами (генерируется из xlsx)
│   ├── localization/             ← Наши e2e-тесты по локализации
│   └── helpers/                  ← Хелперы которые используются ИЗ тестов
│
├── docs/                         ← Документация (этот гайд тут тоже)
├── test-results/                 ← Куда складываются артефакты падений. В .gitignore.
└── playwright-report/            ← HTML-отчёт после прогона. В .gitignore.
```

**Page Object Model (POM)** — паттерн, где каждый «экран» приложения представлен классом. Например `LandingPage` — это класс, который знает где у лендинга кнопка Start и заголовок. Тесты не работают с CSS-селекторами напрямую, они говорят «landing.cta.click()», и POM сам знает что это за элемент.

Зачем: если в приложении переименуют класс кнопки с `.start-btn` на `.btn-primary` — нужно поменять в одном месте (POM), а не во всех 20 тестах.

## 5. Как запустить тесты — короткие команды

| Команда               | Что делает                                                               |
| --------------------- | ------------------------------------------------------------------------ |
| `npm test`            | Полная матрица: 60 projects, ~45 минут                                   |
| `npm run test:smoke`  | Только EN × все девайсы × оба движка (6 projects, ~3–5 мин)              |
| `npm run test:headed` | То же что `npm test`, но с открытым окном браузера (увидишь как кликает) |
| `npm run test:ui`     | Открывает интерактивный UI-режим Playwright. Очень удобно при отладке.   |
| `npm run test:debug`  | Запускает в дебаг-режиме. Останавливается перед каждым действием.        |
| `npm run test:report` | Открывает в браузере HTML-отчёт от последнего прогона                    |

**Точечные запуски** (когда не хочется гонять всё):

```bash
# Только один project — одна комбинация языка/девайса/движка
npx playwright test --project=ru__iphone17__webkit

# Все project-ы для русского языка
npx playwright test --project='/ru__.*/'

# Все project-ы для iPhone 17 (любая локаль, любой движок)
npx playwright test --project='/.*__iphone17__.*/'

# Один конкретный файл с тестами
npx playwright test tests/localization/landing.spec.ts

# Только тесты в названии которых есть слово "paywall"
npx playwright test --grep paywall

# Комбинация всех фильтров
npx playwright test --project=ru__iphone17__webkit --grep paywall
```

**Если хочется запустить ОДИН тест ОЧЕНЬ долго в дебаге:**

```bash
PWDEBUG=1 npx playwright test tests/localization/landing.spec.ts --project=ru__iphone17__webkit
```

Откроется браузер + Playwright Inspector. Ты сможешь по шагам пробежать тест и видеть что происходит.

## 6. Как смотреть отчёт после прогона

После любого прогона (если он завершился) можно открыть красивый HTML-отчёт:

```bash
npm run test:report
```

Откроется браузер с отчётом. Что там есть:

- **Список тестов** с группировкой по project (видно сразу: на каких языках упало).
- **Зелёные/красные значки** — статус каждого теста.
- **Для упавших тестов:**
  - Скриншот момента падения.
  - Видео всего прогона теста (можешь промотать и посмотреть что произошло).
  - **Trace viewer** — самое мощное. По шагам: что Playwright делал, что приходило по сети, какой был DOM. Кликаешь шаг → видишь снимок страницы на этом моменте.
- **Для visual-тестов:** показываются 3 картинки рядом — baseline (что ожидали), actual (что увидели), diff (разница красным).

Если отчёт не открывается командой — открой папку `playwright-report/` руками и кликни `index.html`.

## 7. Что делать, если тест упал

Первый рефлекс новичка: «давай ещё раз запущу». Второй рефлекс: «давай добавлю `waitForTimeout`». Оба рефлекса — НЕправильные.

### Правильный подход

#### Шаг 1: Прочитай сообщение об ошибке внимательно

Playwright говорит ОЧЕНЬ конкретно что произошло. Например:

```
Error: expect(received).toContainText(expected)
Expected substring: "Ходьба"
Received string:    "Walking"
```

Это значит — тест ожидал русский перевод, а получил английский. То есть приложение НЕ переключило язык. Это БАГ в приложении (а не в тесте).

Другой пример:

```
TimeoutError: page.click: Timeout 30000ms exceeded.
Call log:
  - waiting for locator('button[name="Start"]')
```

Значит — кнопки нет на странице (или она названа не так). Возможные причины:

1. Лендинг не загрузился вообще (network проблема).
2. Изменилась разметка приложения (надо обновить локатор в POM).
3. Кнопка действительно не отрисовалась — это баг приложения.

#### Шаг 2: Посмотри HTML-отчёт

`npm run test:report` → найди упавший тест → посмотри скриншот и видео.

Часто сразу видно: «а, на странице вообще ничего не отрисовалось» или «а, кнопка изменила название с "Start" на "Continue"».

#### Шаг 3: Посмотри trace

В отчёте на упавшем тесте — есть кнопка `Trace`. Это пошаговая запись всего что Playwright сделал. Кликаешь шаг → видишь скриншот ИМЕННО ЭТОГО МОМЕНТА + DOM + network requests.

Самое полезное чтобы понять «что было до» и «что случилось не так как ожидалось».

#### Шаг 4: Воспроизведи локально вручную

```bash
PWDEBUG=1 npx playwright test --project=<тот же project> <тот же файл>
```

Откроется браузер. Делай шаги вместе с тестом — увидишь в реальном времени.

#### Шаг 5: Понять что чинить — баг приложения или тест?

- Если упало на одной локали (например ru) а на en — зелёное → скорее всего БАГ ПРИЛОЖЕНИЯ (где-то не подтянулся русский перевод). Заводи тикет.
- Если упало на ВСЕХ локалях → скорее всего тест устарел (изменилась разметка). Чинить тест.
- Если упало нестабильно (бывает зелёное, бывает красное) → ФЛЕЙК. Это худшее. См. ниже.

### Что НЕ делать

❌ Не запускай тест 5 раз подряд в надежде «может пройдёт». Это маскирует флейк, а не чинит его.
❌ Не добавляй `await page.waitForTimeout(3000)` — это плохая практика, она маскирует race condition, не решает.
❌ Не комменти тест с пометкой «потом починим». «Потом» не наступит.
❌ Не делай `git commit --no-verify` чтобы обойти красные тесты — pre-commit хуки существуют не просто так.

### Как чинить флейк (нестабильный тест)

Флейк — это самая неприятная категория. Тест то зелёный, то красный. Обычно причины:

1. **Гонка** — тест проверяет элемент до того как он отрисовался. Чинится использованием `await expect(locator).toBeVisible()` вместо `expect(await locator.isVisible()).toBe(true)`. Web-first ассерты Playwright сами ждут до 10 секунд.
2. **Анимация** — кнопка ещё двигается, тест по ней кликает мимо. У нас глобально выключено через `animations: 'disabled'`, но иногда не помогает.
3. **Сеть** — приложение медленно ответило. Решается ожиданием `networkidle` после критических действий.

Если нашёл флейк — НЕ молчи, скажи команде. Один флейк сегодня = десять флейков завтра = вся команда не верит тестам.

## 8. Что такое snapshot и как с ним жить

### Что это

**Snapshot** (он же baseline screenshot) — это PNG-файл, который мы один раз сделали и сохранили как «эталон». Каждый следующий прогон теста сравнивает свежий скриншот с этим эталоном.

Если они одинаковые — ✅. Если отличаются больше чем на 2% пикселей — ❌.

Хранятся в `tests/localization/<test>.spec.ts-snapshots/<test-name>-<project-name>.png`. Например:

```
visual.spec.ts-snapshots/
  landing-en__iphone17__chromium.png
  landing-ru__iphone17__chromium.png
  ...
```

У нас ~54 snapshot-а — НЕ для каждой комбинации (это было бы 180+, слишком дорого поддерживать). Только для критичных экранов: лендинг, первый шаг опросника, paywall. Подробности — в `docs/superpowers/specs/2026-05-26-e2e-localization-design.md` §8.3.

### Когда они падают

1. **В приложении что-то реально изменилось** (новая кнопка, изменили цвет, поменяли шрифт). Это ХОРОШО — тест поймал регрессию.
2. **Изменился перевод** — допустим в xlsx обновили русское слово с «Ходьба» на «Прогулки». Snapshot покажет diff. Это тоже хорошо.
3. **Изменилась наша baseline** (кто-то её обновил неправильно).

### Что делать когда snapshot упал

1. Открой HTML-отчёт: `npm run test:report`.
2. Найди упавший visual-тест.
3. Посмотри **три картинки рядом**: ожидаемая, актуальная, diff.
4. Реши:
   - **Если изменение в приложении ОЖИДАЕМОЕ** (например мы знали что разработчики делают рефакторинг лендинга): обнови baseline:
     ```bash
     npm run test:update-snapshots
     ```
     Эта команда перезапишет baseline-ы свежими скриншотами. **Проверь diff в git** перед коммитом — убедись что обновились только те snapshot-ы которые ты ожидал.
   - **Если изменение неожиданное** (никто не предупреждал) — это БАГ. Заводи тикет, не обновляй baseline.

### Когда обновлять baseline-ы

```bash
# Обновить ВСЕ snapshot-ы
npm run test:update-snapshots

# Обновить только snapshot-ы одного теста
npx playwright test --update-snapshots tests/localization/visual.spec.ts

# Обновить только для одного project
npx playwright test --update-snapshots --project=ru__iphone17__webkit
```

После обновления:

1. Сделай `git diff` — увидишь какие PNG поменялись.
2. Открой их визуально (в VS Code: правый клик → Open Preview) и убедись что они выглядят правильно.
3. Только потом коммить.

## 9. Как обновить переводы (новый xlsx)

Команда локализации присылает обновлённый `WWLI Onboarding Localisation.xlsx`. Что делать:

### Шаг 1: Заменить файл в репо

Положи новый xlsx в корень репо, заменив старый. Имя файла должно остаться тем же.

### Шаг 2: Проверить что importer его понимает

```bash
npm run i18n:import
```

Что произойдёт:

- Если xlsx имеет правильную структуру (есть колонки key, en, fr, ...) — пересоздаст JSON-ы.
- Если что-то поменялось в структуре (переименовали колонку, удалили sheet) — упадёт с понятным сообщением. Тогда надо разбираться с командой локализации.
- Если в xlsx есть дубликат ключа в разных sheet-ах с разными переводами — упадёт. Надо чинить xlsx.

### Шаг 3: Посмотреть diff JSON-фикстур

```bash
git diff tests/fixtures/i18n/
```

Увидишь какие строки изменились на каких языках. Иногда это сотни изменений — это нормально.

### Шаг 4: Запустить тесты

```bash
npm test
```

Тесты, которые упадут, покажут где приложение **не догнало** новые переводы (т.е. в xlsx уже есть новый текст, но приложение ещё рендерит старый).

Это — повод поговорить с командой разработки приложения, чтобы они задеплоили свежие переводы.

### Шаг 5: Обновить snapshot-ы (если переводы изменились)

Если поменялись строки которые видны на snapshot-экранах (landing/paywall) — snapshot-ы упадут даже если приложение всё правильно отрендерило. Это нормально. Обновляй baseline-ы:

```bash
npm run test:update-snapshots
```

### Шаг 6: Закоммитить вместе


## 10. Как написать свой простой тест

Допустим ты хочешь добавить новый тест: «на лендинге есть кнопка "Read more" в футере и при клике она ведёт на /terms».

### Шаг 1: Открой live-приложение в браузере

`https://dev.slimkit.health/walking/survey/?stripeV64=true` (пароль `dev`/`gPgFCeJ7`).

Найди в DevTools интересующий элемент:

- Inspect → правый клик на «Read more» → Inspect.
- Посмотри: есть ли у элемента `data-testid`? Есть ли уникальный текст? Какой `role` у элемента (`button`, `link`)?

Хорошие признаки для надёжного локатора:

- `data-testid="footer-read-more"` — самое лучшее, не зависит ни от стилей, ни от текста.
- `<a href="/terms">Read more</a>` — можно искать по тексту через `getByRole('link', { name: 'Read more' })`.

### Шаг 2: Если элемент часто-используемый — добавь его в POM

Открой `src/pages/LandingPage.ts`. Добавь геттер:

```ts
get readMoreLink() {
  return this.page.getByRole('link', { name: /read more/i });
}
```

(`/read more/i` — регексп с флагом `i` = case-insensitive. На случай если переведут как «Read More» или «read more».)

### Шаг 3: Напиши тест

Создай файл `tests/localization/read-more.spec.ts`:

```ts
import { test, expect } from '../../src/fixtures/i18n.fixture';
import { LandingPage } from '../../src/pages/LandingPage';

test('footer "Read more" link navigates to /terms', async ({ page, context, i18n }) => {
  const landing = await new LandingPage(page, context, i18n).goto();

  await expect(landing.readMoreLink).toBeVisible();
  await landing.readMoreLink.click();

  // Проверяем что URL содержит /terms
  await expect(page).toHaveURL(/\/terms/);
});
```

### Шаг 4: Запусти ТОЛЬКО этот тест в headed-режиме

```bash
npx playwright test tests/localization/read-more.spec.ts --project=en__iphone17__chromium --headed
```

`--headed` = открой реальный браузер чтобы я видел что происходит.

Что ты ожидаешь:

- Браузер открывается.
- Загружается лендинг.
- Playwright кликает на «Read more».
- URL меняется на `.../terms`.
- Тест PASS.

### Шаг 5: Если что-то не так — итерация

Тест упал? Запусти в дебаг-режиме:

```bash
PWDEBUG=1 npx playwright test tests/localization/read-more.spec.ts --project=en__iphone17__chromium
```

В Playwright Inspector ты можешь:

- Пошагово выполнять тест.
- Делать `await page.pause()` в коде — Playwright остановится в этом месте и даст тебе ползать по странице руками.
- Записать новый локатор кликнув по элементу в браузере (Pick locator кнопка в Inspector).

### Шаг 6: Прогон на нескольких локалях

Когда тест работает на EN, попробуй на других:

```bash
npx playwright test tests/localization/read-more.spec.ts --project=/ru__iphone17__.*/
npx playwright test tests/localization/read-more.spec.ts --project=/ja__iphone17__.*/
```

Если падает только на не-EN — возможно ссылка переводится как «Подробнее» / «詳細» — твой локатор `/read more/i` это не найдёт. Решение: использовать i18n-ключ:

```ts
get readMoreLink() {
  // Предположим что в xlsx есть ключ "footer.read_more"
  return this.page.getByRole('link', { name: this.i18n.get('footer.read_more') });
}
```

### Шаг 7: Закоммитить

```bash
git add src/pages/LandingPage.ts tests/localization/read-more.spec.ts
git commit -m "test: footer 'Read more' link navigation"
```

## 11. Глоссарий: термины Playwright и наши

| Термин                      | Что значит                                                                                                                                          |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Test**                    | Один сценарий проверки, описанный в файле `*.spec.ts`. Один `test(...)` блок.                                                                       |
| **Spec file**               | Файл с тестами. У нас `*.spec.ts` в `tests/localization/`.                                                                                          |
| **Project**                 | Конфигурация запуска (язык + девайс + движок). У нас их 60.                                                                                         |
| **Fixture**                 | Объект, который Playwright инжектит в тест автоматически. Например `page`, `i18n`. Мы создали свой `i18n` fixture в `src/fixtures/i18n.fixture.ts`. |
| **Locator**                 | Способ найти элемент на странице. `page.getByRole('button', { name: 'Start' })`.                                                                    |
| **Web-first assertion**     | `expect(locator).toBeVisible()` — сам ждёт пока станет видимым, до 10 сек.                                                                          |
| **Page Object Model (POM)** | Паттерн: каждый экран = класс. У нас `LandingPage`, `SurveyPage`, `PaywallPage`.                                                                    |
| **Trace**                   | Запись всего что Playwright делал в тесте. Открывается в HTML-отчёте.                                                                               |
| **Snapshot / baseline**     | Эталонный скриншот для сравнения. Хранятся в `*-snapshots/`.                                                                                        |
| **Headed / headless**       | С видимым окном браузера / без него. По умолчанию headless (быстрее).                                                                               |
| **Worker**                  | Параллельный процесс выполнения тестов. У нас `50% CPU` локально.                                                                                   |
| **Auto-wait**               | Встроенная функция Playwright: перед кликом дождаться что элемент кликабелен.                                                                       |
| **Locale**                  | Языковая настройка браузера (например `ru-RU`). Влияет на `Accept-Language` и `navigator.language`.                                                 |
| **basic-auth**              | Простейшая HTTP-авторизация: логин/пароль в заголовке. Дёргается через `httpCredentials`.                                                           |
| **i18n**                    | Internationalization. Сокращение «i + 18 букв + n». Просто способ сказать «поддержка языков».                                                       |
| **xlsx**                    | Формат Excel-файла. У нас в нём переводы.                                                                                                           |
| **flaky test**              | Нестабильный тест: иногда зелёный, иногда красный без изменений в коде. Очень плохо.                                                                |

## 12. Куда смотреть когда «вообще ничего не понятно»

В таком порядке:

1. **Сообщение об ошибке** Playwright. Оно обычно очень конкретное.
2. **HTML-отчёт** (`npm run test:report`) → trace упавшего теста.
3. **Документ дизайна:** `docs/superpowers/specs/2026-05-26-e2e-localization-design.md`. Там есть «почему мы так сделали» для каждого решения.
4. **Документ плана:** `docs/superpowers/plans/2026-05-26-e2e-localization-plan.md`. Там по шагам какой файл за что отвечает.
5. **Официальная документация Playwright:** [playwright.dev](https://playwright.dev). Точно есть на нужную тему.
6. **Скриншот ошибки + спросить старшего разработчика.** Не нужно стесняться — лучше потратить 5 минут чужого времени чем 2 часа своего на тупик.

### Полезные ссылки в документации Playwright

- [Locators](https://playwright.dev/docs/locators) — как находить элементы. Самое важное.
- [Web-first assertions](https://playwright.dev/docs/test-assertions) — `expect().toBeVisible()`, `toHaveText()` и т.п.
- [Test fixtures](https://playwright.dev/docs/test-fixtures) — как работают fixtures (`page`, `context`, наш `i18n`).
- [UI Mode](https://playwright.dev/docs/test-ui-mode) — про `npm run test:ui`. Интерактивный режим, очень удобно для отладки.
- [Trace Viewer](https://playwright.dev/docs/trace-viewer) — как пользоваться trace из отчёта.
- [Snapshot testing](https://playwright.dev/docs/test-snapshots) — про `toHaveScreenshot`.
