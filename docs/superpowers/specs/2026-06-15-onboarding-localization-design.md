# E2E-тесты локализации онбординга — Дизайн-спека

**Дата:** 2026-06-15
**Проект:** Manyas e2e
**Тестируемое приложение:** `https://dev.slimkit.health/walking/survey/?stripeV64=true` (DEV)
**Статус:** Утверждено пользователем (ожидает финального ревью этого файла)

> Эта спека заменяет (`supersedes`) предыдущую
> `2026-05-26-e2e-localization-design.md`. Старая спека покрывала paywall,
> pixel-baseline снапшоты и TDD-дисциплину; новые требования — **только
> онбординг**, максимальная простота для 3 QA без опыта автоматизации,
> отказ от хрупких pixel-baseline'ов. Проектируем заново.

## 1. Цель и скоуп

**Зачем нужны тесты:** ускорить ручное тестирование локализаций онбординга.
Тесты должны быть **простыми**: их запускают и при необходимости чинят 3 QA,
ни у кого нет опыта автоматизации.

**Что проверяем на каждом экране онбординга:**

1. **Перевод есть и совпадает с таблицей** — видимый текст якорных элементов
   точно равен ожидаемому переводу для локали (см. §8).
2. **Нет «сырых» i18n-ключей** (`intro_text_0`), пустых мест и английского
   fallback на не-EN локали.
3. **Вёрстка не ломается** — нет горизонтального overflow, тексты не
   обрезаются и не перекрывают друг друга, кнопка «дальше» в зоне видимости.
4. **Скриншот каждого экрана** кладётся в HTML-отчёт — QA глазами сверяет
   корректность перевода и вёрстки.

**Границы прохождения:** онбординг от первого экрана **до** появления paywall.
Признак paywall — в URL `survey` меняется на `plan_ready_v2`. На этом тест
**останавливается; paywall не тестируем и не трогаем**.

**Вне скоупа (явно):**

- Paywall (любая логика после `plan_ready_v2`).
- **Meta in-app браузеры** (Facebook / Instagram) — это нативные webview
  внутри приложений, Playwright не может их реально запустить (можно лишь
  подделать User-Agent, что не воспроизводит реальные quirks). Тестируются
  **вручную на реальных девайсах**.
- Реальные девайсы / облачные сервисы (BrowserStack и т.п.).
- Accessibility, performance, API-тесты.
- CI/CD (можно добавить позже, сейчас только локальный запуск).
- Языки `ar`, `hi` (есть в таблице, но не в нашем наборе).

**Параметры покрытия:**

- **Языки (10):** `en ru fr de it pt es zh ja ko`
- **Девайсы (3):** iPhone 17 Pro, iPhone 16 Pro Max, Samsung Galaxy S20
- **Браузеры (2):** Chrome → Chromium, Safari → WebKit
- **Конфиги:** список в одном файле (§4)

## 2. Технологии

- **Язык:** TypeScript
- **Среда:** Node.js 20 LTS (зафиксировано в `.nvmrc`)
- **Фреймворк:** Playwright Test (`@playwright/test`)
- **Движки:** Chromium и WebKit (ставятся через `playwright install`)
- **Парсер переводов:** `xlsx` (SheetJS) — читает экспорт Google-таблицы
- **Запуск TS-скриптов:** `tsx`
- **Конфигурация:** `dotenv` для кредов
- **Главный артефакт для QA:** HTML-отчёт Playwright со скриншотами всех
  экранов и трейсами упавших тестов.

ESLint / Prettier — опционально (не обязательны, чтобы не усложнять новичкам).

## 4. URL-конфиги (`src/config/configs.ts`) — ключевой файл для QA

Все варианты ссылок описаны в одном массиве. Добавить новый конфиг = добавить
одну строку.

```ts
export const CONFIGS = [
  { name: 'default',         path: '/walking/survey/', params: 'stripeV64=true' },
  { name: 'taichiwalking',   path: '/walking/survey/', params: 'config=taichiwalking&stripeV64=true' },
  { name: 'japanesewalking', path: '/walking/survey/', params: 'config=taichiwalking&stripeV64=true&japaneseWalkingMethod=true' },
];
```

**Правила сборки URL:**

- **A/B форсится в вариант B** автоматически: ко всем URL добавляется
  `AValue=0&BValue=100`. Это одна константа в коде (`FORCE_B`), её можно
  выключить, если потребуется тестировать вариант A.
- Сборка через `URLSearchParams` (корректный escaping, нет дублей параметров).
- Базовый URL и basic-auth — из `.env` (§6 / §10).

**Выбор конфигов на запуске:**

- `TEST_CONFIG=taichiwalking npm test` — гоняет только указанный конфиг.
- Без переменной — гоняются **все конфиги** из списка.

**Разные первые/вторые экраны** (возраст vs гендер и т.п.) у разных конфигов
**не требуют отдельного кода** — их разруливает detect-and-answer (§7).

## 5. Матрица запуска

`10 локалей × 3 девайса × 2 браузера = 60 Playwright-проектов`.

**Конфиги — внутренний цикл внутри спека, а не измерение матрицы.** Это
сделано осознанно: иначе матрица разрослась бы до 180+ проектов. В
`onboarding.spec.ts` идёт цикл `for (const config of selectedConfigs())`,
внутри — тело теста. Так матрица остаётся читаемой (60 проектов), а конфиги
видны в названии теста.

Имя проекта: `<locale>__<device>__<engine>`. Примеры:
`ru__iphone17pro__webkit`, `ja__s20__chromium`.

**Локаль задаётся браузером** через контекст Playwright (`use.locale`):
Playwright автоматически выставляет `Accept-Language`, `navigator.language`,
`navigator.languages` и locale-зависимые `Intl.*` API. Это ровно соответствует
требованию «язык определяется из браузера/девайса» — без URL-параметров и без
переключателя языка в приложении. Дополнительно ставим `timezoneId` для
стабильного рендеринга дат.

**Device descriptors (`src/config/devices.ts`):**

| Девайс            | Viewport (CSS px) | DSR | Движок-эмуляция |
| ----------------- | ----------------- | --- | --------------- |
| iPhone 17 Pro     | ~402 × 874        | 3   | mobile/touch    |
| iPhone 16 Pro Max | ~440 × 956        | 3   | mobile/touch    |
| Samsung Galaxy S20| ~360 × 800        | 3   | mobile/touch    |

Это собственные дескрипторы (встроенных для iPhone 17 Pro / S20 в Playwright
нет). Точные viewport/UA-значения фиксируются в плане имплементации по спекам
производителей. **UA — приближение** (особенно iPhone 17 Pro как новое
устройство); для серверной логики, ветвящейся по UA, требуется real-device
(вне скоупа). Это документируется в README.

## 6. Переводы: Google-таблица → JSON

**Источник:** Google-таблица
(`docs.google.com/spreadsheets/d/<client-sheet-id>`).
QA экспортирует её в `.xlsx` в корень проекта.

**Структура таблицы (по факту, проверено на текущем файле):**

- 3 листа, 15 колонок (`key, en, ru, fr, de, it, pt, es, zh, ja, ko, ar, hi, -, instruction`).
- **Sheet1** (1617 строк) и **Sheet3** (1492 строки): колонка `key` + переводы.
  Sheet3 — новая редакция; при конфликте ключей **Sheet3 выигрывает**.
- **Sheet2** (226 строк): **без ключей**, параллельные колонки (English как
  идентификатор) → ключ генерируется из английского текста (slugify).
- В начале листов есть **мусорные строки** (`ВАЖНАЯ ИНФОРМАЦИЯ !!!!`,
  пустые `Intro`, `global instruction`) — импортёр их пропускает.

**Поведение импортёра (`npm run i18n:import`):**

1. Читает xlsx из корня. Нет файла → понятная ошибка.
2. Берёт только 10 нужных языковых колонок; игнорирует `ar`, `hi`, `-`,
   `instruction`.
3. **Пропуск строк** (по порядку, первое подходящее → решение), каждый
   пропуск логируется в `_meta.json` (без тихих потерь):
   - пустой `key` или пустой `en` → skip;
   - `key` содержит маркеры `!!!!` / `??` → skip;
   - служебные заметки (например только в `ru`, остальные пусты) → skip.
4. **Дубликаты ключей Sheet1/Sheet3:** Sheet3 обрабатывается первым и
   выигрывает; конфликты логируются в `_meta.duplicateKeys`. Дубликат
   **внутри одного листа** → ошибка (это реальный баг таблицы).
5. **Нормализация значений:** non-breaking space → обычный пробел, trim.
   Литералы `<br/>` и `\n` **сохраняются как есть** в JSON (нормализуются
   позже, при сравнении — см. §8).
6. **Запись:** `tests/translations/<locale>.json` (плоская мапа
   `{ key: value }`) + `_meta.json` (лог импорта).

**Workflow «появились новые переводы»:**

1. Экспортировать Google-таблицу в xlsx, положить в корень (заменить старую).
2. `npm run i18n:import`.
3. `git diff tests/translations/*.json` — увидеть, что изменилось.
4. Запустить тесты — упавшие подсветят, где приложение не совпадает с таблицей.
5. Закоммитить xlsx + JSON вместе.

Импортёр запускается **только вручную**; `npm install` его не дёргает.

## 7. Прохождение онбординга (detect-and-answer)

Один универсальный проходчик в `OnboardingPage`. Алгоритм на каждом шаге:

1. Если в URL появился `plan_ready_v2` → **стоп** (дошли до paywall).
2. Определить тип экрана: выбор одного / выбор нескольких / слайдер / число /
   текстовый ввод / инфо-слайд.
3. Дать первый валидный ответ (детерминированно).
4. Нажать «далее» (если кнопка есть) либо положиться на авто-переход.
5. Дождаться стабилизации следующего экрана (без `waitForTimeout`-магии —
   web-first ожидания Playwright).

Устойчив к **ветвлениям** опросника и к **разным первым/вторым экранам**
разных конфигов (возраст vs гендер). Предохранитель `MAX_STEPS` роняет тест,
если цикл застрял; точное значение калибруется ручным замером и фиксируется
константой с комментарием.

## 8. Проверки — точное сравнение по якорям

**Проблема:** сравнивать **каждый** плавающий текст экрана с таблицей на
ветвящемся опроснике — хрупко и сложно для новичков (надо привязать каждый
DOM-элемент к ключу). Поэтому используем **точное сравнение по якорям**.

### 8.1 Точное сравнение (якорное)

- На **узнанных** экранах `OnboardingPage` знает ключи стабильных элементов
  (заголовок, подзаголовок, CTA, варианты ответа) в виде списка
  `{ selector, key }`.
- Тест проверяет: `normalize(видимый текст) === normalize(перевод[локаль][ключ])`.
- Добавить новый якорь = одна строка `{ selector, key }`.

**Нормализация текста (`src/utils/normalize.ts`) — обязательна с обеих сторон:**

В переводах из таблицы встречаются HTML-теги `<br/>` и переносы `\n`
(например `intro_text_5` = `"Improve my<br/>health for life"`). В браузере
текст рендерится **без** литерала `<br/>`. Поэтому перед сравнением обе строки
прогоняются через:

1. `<br/>` / `<br>` → пробел;
2. `\n`, `\r`, таб → пробел;
3. схлопывание повторных пробелов в один;
4. trim.

Без этой нормализации точное сравнение давало бы массовые ложные падения.

### 8.2 Авто-проверки на каждом экране (узнан он или нет)

Работают всегда, независимо от наличия якорей:

- **Нет сырых ключей:** на экране нет видимого текста, который матчит форму
  i18n-ключа. Регексп ловит оба стиля из таблицы — `snake_case`
  (`intro_text_0`) и `camelCase` (`fitnesLevel_title`), а также `{{плейсхолдеры}}`.
- **Нет EN-fallback на не-EN локали** (эвристика): подозрительно, если на
  локали ≠ en видимый текст совпадает с английским переводом того же ключа.
  Срабатывания ревьюятся, легитимные случаи (бренды, `email`) попадают в
  whitelist.
- **Нет overflow/перекрытий (DOM):** `documentElement.scrollWidth <=
  clientWidth`; элементы с `overflow:hidden` не обрезают контент по факту;
  кнопка «далее» в зоне видимости (`toBeInViewport()`).
- **Скриншот экрана** кладётся в HTML-отчёт (для глазного ревью QA).

### 8.3 Почему не pixel-baseline

Pixel-baseline снапшоты падают при любом изменении текста и требуют
ребейзлайна — это слишком тяжело для QA без опыта автоматизации. Вместо них:
авто-проверки overflow дают pass/fail по поломкам вёрстки, а скриншоты в
отчёте — материал для глазной оценки «красиво/некрасиво».

## 9. Page Object Model

- **`BasePage`** — `goto(config)` (строит URL, чистит `localStorage`/cookies
  через `addInitScript` до загрузки страницы — funnel кеширует прогресс),
  `ready()`.
- **`OnboardingPage`** — `answerCurrentStep()`, `advance()`,
  `isPaywallReached()`, доступ к якорям текущего экрана.

**Правила POM:**

- Никаких захардкоженных видимых строк — всё через `translations.t(key)`.
- Локаторы по приоритету: роль + переведённый текст → `data-testid` →
  `getByLabel`/`getByPlaceholder` → CSS (крайний случай).
- Никаких ассертов внутри POM (ассерты живут в спеке).
- Никаких `waitForTimeout` — web-first ожидания Playwright.

```
BASIC_AUTH_USER=dev
BASIC_AUTH_PASS=<ask-the-project-owner>
```

сам редактирует креды в HTML-отчёте). `.env` в `.gitignore`,

**Типовые команды:**

| Команда | Назначение |
| --- | --- |
| `npm test` | Вся матрица × все конфиги |
| `npm run test:smoke` | Только EN — быстрый прогон |
| `TEST_CONFIG=taichiwalking npm test` | Один конфиг |
| `npx playwright test --project=ru__iphone17pro__webkit` | Одна комбинация |
| `npm run test:report` | Открыть HTML-отчёт |
| `npm run i18n:import` | Обновить переводы из новой таблицы |

## 11. Отчёты и артефакты

HTML-отчёт (`reporter: [['list'], ['html']]`):

- Сгруппирован по проектам — видно, какие locale/device-комбинации упали.
- Скриншот каждого экрана онбординга (вложение к тесту).
- На упавших — trace viewer (timeline, network, DOM), видео, скриншот падения.

`test-results/` и `playwright-report/` — в `.gitignore`.
`screenshot: 'only-on-failure'` для падений; скриншоты экранов для ревью
кладутся явными `attach`-вызовами на каждом шаге.

## 13. Риски и ограничения

| Риск / ограничение | Как обходим |
| --- | --- |
| **WebKit ≠ iOS Safari**, Meta-браузеры вне автоматизации | Честно в README; iOS-specific и Meta-webview баги проверяются вручную на реальных девайсах. |
| UA девайсов — приближение (iPhone 17 Pro новый) | Централизовано в `devices.ts`, легко обновить. Если бэкенд ветвится по UA — нужен real-device (вне скоупа). |
| HTML-теги `<br/>` / `\n` в переводах ломают сравнение | Обязательная нормализация с обеих сторон (§8.1). |
| Таблица может расходиться с живым приложением | Таблица — источник истины; расхождение = баг в триаж. |
| Ветвление опросника → флаки | Детерминированный detect-and-answer (первый валидный ответ). |
| Полная матрица × конфиги долгая | Smoke-сюита; фильтры по проекту и `TEST_CONFIG`. |
| Структура таблицы может измениться (переименуют колонку) | Импортёр валидирует наличие `key` и 10 языковых колонок, падает с понятным сообщением. |

## 14. Критерии успеха

1. `npm install && npm run install:browsers && npm test` запускает матрицу
   60 проектов × конфиги локально без ошибок setup.
2. Неверный/отсутствующий перевод в таблице роняет `onboarding.spec.ts` с
   понятным сообщением, называющим **локаль + ключ + конфиг + шаг**.
3. Сломанная вёрстка (overflow/перекрытие) ловится авто-проверкой; в отчёте
   есть скриншот соответствующего экрана.
4. Тесты не содержат paywall-логики (останавливаются на `plan_ready_v2`).
5. По `docs/beginner-guide-ru.md` новый QA без опыта автоматизации
   запускает тесты и читает отчёт за < 15 минут.
6. Добавление нового конфига = одна строка в `configs.ts`; добавление
   нового якоря = одна строка `{ selector, key }`.
